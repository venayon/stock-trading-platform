# Local latency, CPU and memory baseline — 24 October 2026

**10 offered trades/second passed the configured local gates. 20 failed.** This establishes a tested point and an
overloaded point, not the exact maximum or a production sizing certificate.

Implementation and commands: [load-generator README](../../load-generator/README.md). Structured
evidence: [baseline JSON](local-baseline-2026-10-24.json). Original local artifacts are under
`load-generator/reports/perf/c4137976-31f1-4be0-887c-d651329c980c/`; they are ignored runtime outputs.

## Experiment

```sh
RATES=10,20 DURATION_SECONDS=30 WARMUP_SECONDS=10 BASELINE_SECONDS=5 npm run test:perf
```

Both Java services ran on the host without harness-imposed CPU/RSS limits. Environment: macOS x64, 16 logical host CPUs,
32 GiB host RAM; Docker had 16 CPUs visible and about 7.75 GiB memory. The privileged test runner reported Node 20.16.0,
with pinned Playwright 1.49.1. Shared local Kafka/Mongo/Registry and monitoring services remained running.

Workload: fresh POST trades, alternating BUY/SELL, deterministic twelve-symbol cycle, exact decimal prices, maximum 16
concurrent POSTs. Completion was sampled every ten offered slots with up to 32 observers; every accepted ID was
reconciled after its stage. The experiment included a ten-second excluded warm-up. Resource sampling used direct app
metrics, host JVM RSS and Docker stats. No application resource cap was applied or validated.

Starter gates: acceptance p95 ≤250ms, observed completion p95 ≤5000ms, errors/dropped slots ≤1%, producer pending and
consumer committed-lag growth ≤0.5 offset/record units per second, complete reconciliation and healthy telemetry. These
are test assumptions, not business-approved SLOs.

## Results

| Offered trades/s |  Requests issued | Successful POSTs | POST p95 | Sampled COMPLETE p95 | Completion samples | Pending slope | Committed lag slope | Result |
|-----------------:|-----------------:|-----------------:|---------:|---------------------:|-------------------:|--------------:|--------------------:|--------|
|               10 |              300 |              300 |  12.82ms |               1052ms |                 30 |      +0.188/s |            +0.003/s | PASS   |
|               20 | 597 of 600 slots |              597 |  13.22ms |               5104ms |                 59 |      +2.378/s |            +0.024/s | FAIL   |

No issued request returned an HTTP/network error. At 20 RPS, three slots were missed by the generator scheduler (0.5%);
none were hidden, and this was within the configured 1% tolerance. Neither repeat-stage observer saturated. All 897
measured accepted trades reached COMPLETE and passed route/value reconciliation. A separate 100-trade warm-up also
completed.

The 20 RPS failure is not data loss. Acceptance stayed fast, but pending intent accumulated and observed completion
exceeded its gate. Poll-observed completion includes a 500ms polling interval plus scheduling/network overhead, so it is
an upper bound rather than an exact server completion time. The independently failed backlog-growth gate is stronger
evidence of non-steady behavior than the small margin above the completion threshold.

An earlier exploratory 5/10/20 run also passed 5 and 10 and failed 20; it saturated the initial eight-observer
measurement pool at 20. That run was not used for the final completion estimate. A subsequent standalone 10 RPS
Playwright regression profile passed.

CPU is cumulative process CPU-time delta divided by sample elapsed time. Values are core equivalents, not host CPU
percentages. RSS is ps-reported resident memory for verified Java PIDs; heap/nonheap are Micrometer values. Maxima may
occur at different instants, so do not add every independent maximum as though it were one simultaneous sample.

|--------------------|---------------------------|----------:|-------------------------:|-------------|

| ms_trade_processor | 0.25 / 0.5 core           |   192 MiB |                  832 MiB | UNVALIDATED |

These are formula-generated starting points for a constrained retest, **not tested deployment settings**. The formulas
and headroom assumptions are documented in the harness README. An observed low used heap does not prove a smaller Xmx
will preserve GC latency or startup behavior. Memory outside used heap is material, and CPU quotas can alter JVM
ergonomics and tail latency.

The Playwright worker averaged about 0.201 CPU cores, with sampled p95 1.057 cores and peak RSS 173.7 MiB across the
whole experiment. CPU can exceed one core over a sample because the process includes helper/native threads. Parent
test-runner overhead is not included. This confirms that the load generator consumes resources too; it is not evidence
that all scheduling jitter was eliminated.

At 10 RPS, completion observation plus final reconciliation made 378 GET requests; at 20, 1067 GETs. Metrics polling
added approximately two requests/second. Existing Prometheus scraping also continued. Interpret sizing for this measured
workload-plus-observation mix, not for an isolated write-only service.

## Likely bottleneck and next experiments

The evidence localizes growth to the producer's durable publication queue: REST acceptance remained fast while consumer
committed lag stayed nearly flat.
The [publication scheduler](../../ms_trader/src/main/java/com/example/finance/trader/publication/PublicationScheduler.java)
handles at most 20 records, then waits a one-second fixed delay. With nonzero batch work, its ceiling is below 20
publications/second:

```text
throughput ceiling ≈ 20 / (1 second + time to process one batch)
```

That configuration is consistent with the observed pending growth. It does not identify how much individual send time
belongs to MongoDB, Kafka or JVM work. Do not increase CPU alone and assume it removes this limit.

1. Validate the candidate heap/CPU/memory budgets under actual OS/container limits. Collect throttling, GC and
   native/RSS behavior; ActiveProcessorCount alone is not a CPU limit.
2. Profile publication attempts, then consider batch/poll/concurrency changes while preserving lease and duplicate
   semantics. Keep correctness tests unchanged.
3. Refine the passing/overloaded boundary with intermediate rates (for example 12, 15, 17, 18) and repeat runs. Ten is
   the highest passing point **tested here**, not a proven maximum.
4. Run longer steady-state and soak tests, cold starts and different stage orders. Thirty-second samples cannot
   establish leak-free operation or strong p99 confidence.
5. Test larger payloads, key skew, read/replay mixes and dependency failures. Keep measurement overhead explicit and use
   a separate generator host for higher loads.

The source matrix's overall Playwright result is intentionally FAIL because one offered stage violated the gates. The 10
RPS regression profile, 22 API cases and seven analyzer cases passed. Raw evidence is preserved; the test does not
change thresholds or retry failed stages to manufacture a green result.
